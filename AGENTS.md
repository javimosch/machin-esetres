# AGENTS.md — machin-esetres

Architecture notes, decisions, and open questions for whoever (human or agent)
picks this up next. This file is the source of truth for *why*, not just
*what* — keep it current as decisions get made or revisited.

## Origin

poche-resend-webmail's "Honest limitations" README section calls out: sent
attachment bytes live on the app server's local filesystem
(`blobstore.go` / `BLOB_DIR`), not in poche (poche keeps documents in memory —
6MB of base64 blob data once pushed its RSS from 4MB to 315MB, which is why
attachments were never stored *in* poche to begin with). No dedup, no HTTP
API, single host, no HA story beyond `tar czf` by hand.

Decided 2026-08-08: build a proper self-hosted object store in machin rather
than keep extending the ad hoc blob store, because (a) poche's own `_files`
collection has the identical gap — GET works, no HTTP upload route — so this
is really *two* ad hoc blob stores in the ecosystem that could be one real
service, and (b) machin already has almost all the plumbing (`machweb.src`
has binary-safe bodies, multipart parsing, streaming responses, HMAC signing;
`machin-kv` proves the SQLite-index pattern) — this is closer to "assemble
existing parts" than "build a storage engine from scratch."

## Decisions made (2026-08-08 design pass)

| Question | Decision | Why |
|---|---|---|
| API scope | Phase 1: custom REST (bucket/key, bearer token). Phase 2 (committed, not speculative): real AWS SigV4-compatible facade over the same object model. | Phase 1 fixes poche-resend-webmail's actual problem without the SigV4 lift. Phase 2 is what makes this a genuine MinIO alternative rather than "S3-flavored." Explicitly requested, not deferred indefinitely. |
| Deployment host | rbm21 (100.123.0.125 via Tailscale), not colocated with poche-resend-webmail on dk1. | Separate failure domain — the whole point of moving attachments off a single app server's disk is defeated if the object store shares that server. rbm21 already has zig/gcc for a native build. |
| Exposure | Internal only, over Tailscale. No public Traefik route. | It's a backend service other machin-ecosystem apps talk to, not something end users hit directly. |
| Tenancy | Bucket-per-mailbox. | Matches poche-resend-webmail's existing per-mailbox model (own Resend creds, own quota) — attachments for different clients (e.g. La Cure) stay cleanly separable, deletable, and backup-able independently. |
| Dedup | Content-addressed by sha256, refcounted, at the storage layer — not a feature flag, just how objects are laid out on disk. | Free win once you're building fresh rather than extending `blobstore.go`'s random-ID layout. |
| Index | SQLite per bucket (`<bucket>/index.db`), not one global DB. | Buckets stay independently movable, deletable, and backup-able as a unit — consistent with the bucket-per-mailbox tenancy decision. |
| Bucket create/delete over HTTP | CLI-only in Phase 1, no HTTP route. | One less auth concept (no separate admin token) for a decision that doesn't need to happen over the network — `serve` only ever handles object ops against buckets that already exist. |
| HEAD semantics | Returns JSON metadata (`{"size":...,"content_type":...}`), not a real bodyless HTTP HEAD. | `machweb`'s Content-Length is computed from the body actually being written; faking an empty-body 200 for a non-empty object meant either a wrong (0) Content-Length or a second, conflicting one — both invalid HTTP. Caught by testing against a live server before deciding this was fine to ship, not assumed. Real HEAD semantics are a Phase 2 concern. |
| Token storage | Plaintext in `buckets.db`, generated by the CLI (`bucket create`), printed once, masked (`abc…wxyz`) everywhere else (`bucket list`). | Matches this ecosystem's existing threat model for local secrets (poche-resend-webmail's own `webmail.env` tokens are plaintext on disk, access-controlled by file permissions, not encryption) — not gold-plating a threat model the rest of the stack doesn't have either. |
| Phase 2 credential mapping | `access_key_id = bucket name`, `secret_access_key = bucket token` — no separate S3 credential store. | Reuses the exact registry Phase 1 already has. One identity per bucket either way; inventing a second credential concept would be pure overhead. |
| Phase 2 routing | Path-style S3 routes (`/<bucket>/<key>`) live alongside Phase 1's `/b/<bucket>/o/<key>` in the same `handle()` dispatch — anything not under `/b/` falls through to the S3 facade. | No new port/process needed; one binary serves both protocols over the same buckets. A bucket literally named `b` would collide with Phase 1's namespace — accepted as a reserved-name edge case, not worth solving. |
| Phase 2 HEAD | Sends the same body a GET would (not a spec-correct empty body). | Same `machweb` Content-Length constraint that shaped Phase 1's HEAD — see the "Reference" section below. Verified sufficient for real clients: `aws s3api head-object` (botocore) only reads headers and was fine with it. |
| Phase 2 error format | AWS-shaped XML (`<Error><Code>...</Code>...</Error>`) mirroring real S3 error codes (`NoSuchBucket`, `NoSuchKey`, `SignatureDoesNotMatch`) rather than a generic message. | `aws-cli` parses these into its real, recognizable error output — verified live, not assumed from the S3 spec alone. |

## Open questions (not yet decided — resolve before or during Phase 1)

- **Token rotation**: `bucket create` mints a token once; there's no `bucket
  rotate-token <name>` yet. Should probably mirror poche-resend-webmail's own
  `readSecretFlag` pattern (stdin or `env:NAME`, never argv) if/when a
  CLI-supplied (rather than always-generated) token is needed.
- **poche-resend-webmail's migration path**: does `blobstore.go` get replaced
  outright (attachments only ever live in machin-esetres going forward), or
  does it become a two-tier cache (recent/hot attachments on local disk,
  everything else in machin-esetres)? Affects whether Phase 1 needs a
  bulk-migrate-existing-attachments tool from day one.
- **Backup story**: machin-esetres's own data directory is a natural
  machin-vault `file` target (rsync-based) — should it be, from day one, or is
  that a separate follow-up once the service exists and has real data?
- **rbm21 disk**: deployed 2026-08-08 with 14G free (76% used), no dedicated
  volume/mount. Not yet a problem (no real buckets provisioned) but resolve
  before this holds production attachment data — see
  `~/backups/machin-esetres/access.txt` for the live deployment record.
- **List pagination**: Phase 1 shipped with none — `GET /b/<bucket>?prefix=`
  returns every matching row in one response. Fine for a mailbox's attachment
  list (dozens, not millions); revisit before this is used for anything with
  large buckets. When it's added: an opaque cursor backed by the SQLite index
  (last key + limit) vs. something S3-shaped (`ContinuationToken`) to reduce
  Phase 2 rework — leaning toward the latter since Phase 2 is committed.
- **`LIKE` prefix escaping**: `obj_list_body`'s prefix filter doesn't escape
  `%`/`_` — a key containing a literal `%` would behave as a SQL wildcard, not
  a literal match. Not fixed in Phase 1 (unlikely for mail attachment paths);
  fix with a `LIKE ... ESCAPE` clause if it ever bites.
- **Multipart uploads for large objects**: out of scope until `machweb`
  grows streamed (not fully-buffered) request bodies — see the platform
  constraint in README.md. Not needed for mail attachments today; revisit if
  a real use case needs it (per this ecosystem's usual pattern of a real
  project driving the machin feature, not building it speculatively).
- **Phase 2 presigned URLs and chunked SigV4**: not implemented — see
  README.md's "Phase 2 scope limits". Add if a real client/workflow needs
  them (e.g. a browser downloading via a presigned link, or an SDK that
  defaults to chunked signing for large uploads).
- **`machweb-headers`/`machweb-bytes-body` remote branches**: `~/ai/machin`
  has unmerged remote branches (`feat/machweb-headers`, `feat/machweb-bytes-body`,
  `machweb-linear-body-read`, `fix/machweb-full-body`) that, by name, may
  already address the "can't send a non-zero Content-Length with an empty
  body" gap behind both Phase 1's and Phase 2's HEAD workarounds. Not
  investigated or merged — deliberately out of scope for this pass (pulling
  in unreleased framework changes is a bigger, riskier task than working
  around the gap, and machweb is shared infrastructure other projects
  depend on). Worth checking before spending more effort on HEAD compliance.

## Reference: what machin already provides (verified 2026-08-08)

Grounded by reading `~/ai/machin/framework/machweb.src` and sibling projects
directly — not assumed.

- **`machweb.src`** (`serve(port, handler)`): binary-safe request bodies
  (`body_bytes bytes`), `parse_multipart`/`multipart_file`/`multipart_field`
  for `multipart/form-data`, `header`/`query`/`param`/`cookie` accessors,
  streaming responses (`stream_response`, `sse`, `hijack` for protocol
  upgrades), HMAC-signed sessions (`session_sign`/`session_verify`,
  `set_session`/`get_session`), `serve_tls` for direct TLS (not needed here —
  Tailscale + internal-only). Request body is read fully into memory based on
  `Content-Length` — see the platform constraint above.
- **SQLite builtins** (`sqlite_open`/`sqlite_exec`/`sqlite_query`, proven in
  `machin-kv` and `machin-web-demo-users`): `sqlite_query` returns a JSON
  array, composes with `json_get`. Bound-parameter execution
  (`sqlite_exec(db, "... VALUES(?, ?)", []string{...})`) is injection-safe —
  use it for the index, not string-concatenated SQL.
- **`flags.src`** (vendored across every machin CLI in this ecosystem,
  canonical copy in `machin/framework/`): short/long flags, `=`/space value
  forms, bool flags, defaults, positionals, auto `--help`. Use it rather than
  hand-rolling argument parsing.
- **The house agent-first contract** (established by machin-vault, formalized
  further by the `agent-first-cli-specs` skill): versioned envelope
  (`{"version":"1","ok":...}`), errors on stderr in the same shape, semantic
  exit-code bands (`0` ok · `80-89` bad input · `90-99` not found · `100-109`
  integration failure · `110-119` internal), `help-json` self-description,
  destructive actions refuse without an explicit `--yes`/`--force`. Reuse
  this verbatim rather than inventing a new contract.

## Non-goals (explicit, so they don't get assumed later)

- Fixing poche-resend-webmail's *inbound* attachment gap (needs a
  read-capable Resend API key — unrelated to where sent attachments are
  stored).
- Multi-region replication, erasure coding, or anything MinIO-cluster-shaped.
  This is one binary, one data directory, on one box (rbm21) — HA here means
  "not sharing a disk with the app server and having a real backup story," not
  "distributed consensus."
- Byte-for-byte MinIO API parity in Phase 1. Phase 2's SigV4 facade targets
  "existing S3 clients work," not "every MinIO-specific extension works."
- `-` (stdin) support for `put`/`get`. `put` needs a real file path (`read_file_bytes`
  needs a path — `read_stdin()` returns a `string`, not `bytes`, so it isn't
  provably NUL-safe for arbitrary binary content); `get` always needs `--to <file>`.

## Verified (2026-08-08, Phase 1 implementation)

Not just "compiles" — `smoke.sh` builds the actual shipping binary and drives
it end-to-end:
- CLI: `bucket create` mints a token; `put`/`get` round-trip a file byte-for-byte
  (`diff` against the original); `ls` lists it; a missing key on `get` exits
  `90` with an `{"ok":false,...}` envelope on stderr, not a crash.
- Dedup + refcounting: two different keys with identical bytes share one blob
  file on disk; deleting the first key leaves the blob in place (refcount
  2→1); deleting the second key removes it (refcount 1→0). Confirmed by
  checking the actual blob file's existence on disk at each step, not just
  the SQLite rows.
- HTTP: no/wrong bearer token → 401; unknown bucket → 404; `PUT` → `GET`
  round-trips the same bytes as the CLI path; `HEAD` returns metadata with a
  single correct `Content-Length` (this is what caught the double-header bug
  above); prefix list finds the uploaded key; `DELETE` then re-`GET` → 404.
- `sha256sum` cross-check: the CLI's reported digest matched real `sha256sum`
  on the same file, not just machin's own `sha256_bytes` used both to store
  and to verify (which would validate internal consistency, not correctness).

## Verified (2026-08-08, Phase 2 implementation)

Against a genuine `aws-cli` — not our own signer testing our own verifier,
which would only prove internal self-consistency:
- `aws s3 cp` upload, `aws s3 ls`, `aws s3 cp` download with a byte-identical
  `diff` against the original, `aws s3api head-object` returning real
  metadata, `aws s3 rm`.
- A wrong `AWS_SECRET_ACCESS_KEY` is rejected with AWS's own real
  `SignatureDoesNotMatch` error — not a generic 401/403.
- A nonexistent bucket returns AWS's own real `NoSuchBucket` error, parsed
  correctly by aws-cli into its normal error output.
- Caught and fixed one real integration bug via this testing, not
  assumption: `aws s3 cp` (download) internally calls `HeadObject` first and
  hard-failed parsing the response with `fatal error: 'LastModified'`
  because that header was missing — fixed by adding `Last-Modified` (from
  the object's `created_at`) to both GET and HEAD responses.
- `./smoke.sh` now runs this whole Phase 2 flow automatically (skips
  gracefully if `aws-cli` isn't installed, so the test stays portable).

## Verified (2026-08-08, deployment)

- Built `--static` (bundles SQLite + OpenSSL), gated locally (bucket create +
  serve + health check against the exact binary) before shipping — same
  discipline as poche-resend-webmail's release process.
- Running as a systemd service (`machin-esetres.service`) on rbm21 under a
  dedicated system user (`esetres`), auto-restart on failure.
- Health-checked and round-tripped an object (Phase 1 API AND Phase 2 S3
  facade via aws-cli) from **dk1 over Tailscale** — the actual reachability
  path poche-resend-webmail would use — not just localhost on rbm21 itself.
  Verification bucket deleted afterward; no real buckets provisioned yet.

Not yet verified: load/concurrency behavior (machweb is one goroutine per
connection — see the machin-backend skill's pooling guidance; this
implementation doesn't pool SQLite connections, opening a fresh
`sqlite_open` per request instead, which is correct but unmeasured under
concurrent load), and behavior once rbm21's disk actually fills with real
attachment data.
